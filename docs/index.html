fintech-lab

Six fintech projects on the standard library. Three products — an ISO 8583 payment-message workbench, a lending-policy sandbox, and a transaction assistant for Roman Urdu — and three that ask a local model to do those same jobs and are scored by the products' own graders.

No dependencies anywhere, and no model needed for the first three: the thing deciding the outcome is small enough to read, and what grades it is deterministic code rather than a model's opinion. That is also what makes the model arms worth anything — there is a baseline on the same cases that does not move.

The model arms — the same jobs, asked of a local model

Each one asks a local model to do what its pair does with code, and is scored by that pair's own grader. The deterministic version is in every comparison table, because a model number with no baseline beside it invites the reader to supply their own idea of what good looks like. Every reply is cached and the cache is committed, so the numbers can be rechecked without a GPU.

What each project is measured on

Every project is scored on between 50,000 and a million rows. Two of these datasets are public files that get downloaded and five are generated from a seed; none of them is in the repository, which ships the generators, a 200-row sample of each and a manifest of row counts and sha256 fingerprints. The dashboards run locally, and that is not a limitation being hidden

Each project serves a single-page dashboard, an input/output proof at /io, and its own request counters. They need a Python process, and this page is static files on GitHub Pages, so they are not hosted here. One command brings all three up together with a control panel in front of them: 

git clone https://github.com/hammasbuilds/fintech-lab
cd fintech-lab
uv run python -m observatory --start-all      # then open http://127.0.0.1:8100

The Observatory starts and stops each project, shows whether it is actually answering on its port rather than merely spawned, reads each one's own counters, and links through to every project's dashboard, proof page, dataset page, source and README — so there is one place to open them from instead of a shortcut per project.

Or run one on its own: make serve01, make serve02, make serve03. To see the numbers above without a browser at all: uv run python demo.py.

What is deliberately not flattering

Each project publishes a figure that does not favour it, because the alternative is a page of round numbers that cannot be wrong.

  • Switchboard stops at 97.4% on random framing damage. An ISO 8583 bitmap carries no redundancy, so one flipped bit can swap a field for another of the same width and produce a different valid message. No parser can catch that, which is why the invariant layer exists.
  • Policy Bench reports a Gini of 0.233 and calls it weak separation in those words. Its cohort is synthetic and its generator is written out in full, so every figure is a statement about that generator rather than about a market.
  • Guardian misses every scam that avoids its vocabulary, and the layer that recovers those also slows one ordinary transfer in five. Both halves are measured; reporting only the first would be advertising.
  • The model arms report what they cost and what they could not do: replies that hit the token cap, cases with no cached reply that were therefore not run rather than scored, and the two models excluded from the headline with the reason stated — one does not fit this machine's 16 GB without running partly on CPU, and the other is a base model that answered “reply with OK” with “88888888”.
